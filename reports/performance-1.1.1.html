性能优化实测评测报告

基线 1.1.0（git acb6370） 对照 1.1.1（工作区） 2026-09-07
所有数字都是本机实跑出来的，不是估算。旧版用 git worktree 检出已发布的 1.1.0 单独跑， 新版用同一份工作区代码；两边共用同一段测试素材、同一条参数生成路径， 只有代码自己决定的线程数与私有参数不同。

0一句话结论

这一轮最大的收益不在编码速度，而在界面不再卡和不再悄悄丢音轨。 导入 100 个文件的界面开销降到 1/144，真实素材探测快 2.9×，提交大文件从整盘拷贝变成一次重命名。 编码侧只有 VP9 拿到了 2.18× 的实打实提速；H.265 / AV1 在满负载下的吞吐基本持平， 换来的是 CPU 总占用降低 6~9%。

1测量环境与方法

先说清条件，数字才有意义。

机器Apple Silicon，14 逻辑核（10 性能 + 4 能效）
FFmpeg7.1.1（Homebrew，系统 PATH）
测试素材1920×1080 @30fps / 5s / 双音轨，libx264 CRF 14 生成（91 MB）
素材性质合成内容（testsrc2 + 噪点），绝对耗时不代表真实影片，只看新旧相对差
耗时口径wall = 墙钟秒；CPU = 所有进程 utime+stime 之和（取自 ffmpeg -benchmark）
并行度口径par = CPU ÷ wall，即在飞的平均核数，越大说明越霸占整机
取样每个场景跑 1 轮。差异 <10% 的一律标为「持平/噪声」，不作为结论

2编码速度：只有 VP9 拿到了大收益

单文件场景，1080p / 5s 素材，CRF 档位取各编码默认值（H.265=28，VP9=32，AV1=32，H.264=23）。 新版把线程预算从 8 提到 13，并补上了编码器真正认的私有参数。

VP9 为什么快这么多：新版补上了 -row-mt 1 -tile-columns 2。 旧版只给了 -threads 8，但 libvpx-vp9 的 -threads 只是个「建议值」， 不开 row-mt 时它几乎单线程跑。实测 CPU 时间从 41.0s 涨到 46.1s（多核并行有同步开销）， 但墙钟从 11.58s 砍到 5.32s —— 这正是并行化该有的形状：总工作量略增，等待时间腰斩。
H.265 / AV1 为什么没变快：这两个本来就自动吃满核心（x265 默认建 14 线程池， SVT-AV1 默认并行度 5+），-threads 对它们无效，所以旧版也没吃亏。 新版补的 pools=N / lp=N 是上限约束而非加速手段 —— 它在单任务场景下不会让编码更快， 价值在下一节的并发场景。AV1 体积 +1.5% 是 tune=0（PSNR 取向）换来的画质取向变化，不是退化。

3并发与资源预算：吞吐持平，CPU 占用下降

8 个文件同时编码。这是「资源预算」这批改动的主战场：旧版每个 x265 进程都按自己的默认建满线程池， 8 个进程互相抢；新版按整机预算给每个进程发固定配额。

这一段要说清楚，因为它不是「变快了」。 8 路并发时整机本来就打满（par 11.2 / 10.6 已接近 14 核上限）， 所以限流并不能换来吞吐 —— 墙钟反而慢了 5% 左右，换来的是 CPU 总消耗降 6~9%。 这笔账在用户还要同时用机器时才划算：压缩 8 个视频时浏览器不再卡、风扇不再狂转。 如果你的使用习惯是「开满并发然后走人」，这一项对你没有收益。

4界面响应：从 O(N²) 降到 O(N)

这是本轮最硬的收益。旧版每探测完一个文件，就把「刷新编解码器下拉 + 刷新体积预估 + 重画汇总栏」整套跑一遍， 而这三件事各自都要遍历一遍完整任务列表 —— 于是导入 N 个文件的代价是 N²。 新版改成按内容 diff 的增量渲染 + 120ms 节流批量刷新。

6提交阶段：整盘拷贝变成一次重命名

压缩完成后要把临时产物写回原路径。旧版无条件 copyFile 到同目录 staging 再 rename； 新版先直接 rename，只有跨设备（EXDEV）才回退到拷贝 —— 而临时文件本来就在源文件旁边， 所以常见路径下是 0 次拷贝。

每个任务的提交都省一次全量写盘。批量压 20 个 4K 素材时，光这一项就省下几十秒的纯 I/O， 顺带还少了一倍的 SSD 写入量。

7正确性：这一轮修掉的是「静默损坏」

性能之外的部分，反而更值得说 —— 因为它是不可逆的。

问题1.1.01.1.1实测证据
多音轨素材 丢轨道 全保留 双音轨源：旧版输出 [video, audio]，新版 [video, audio, audio]
压缩后反而变大 照写回原文件 跳过，保留原件 提交前比对，小于阈值不动原文件
取消任务 直接 SIGKILL SIGTERM → 800ms → SIGKILL 给 ffmpeg 留出收尾时间，避免留下半截文件
临时文件可见性 Eagle 能扫到 点号前缀 + 注册表 临时产物不再出现在素材库里
为什么旧版会丢音轨：主编码流程里一个 -map 都没有，完全依赖 ffmpeg 的默认流选择， 而默认规则是「每种流类型只挑一条最好的」。双语轨、评论轨、5.1+立体声这类素材压完就只剩一条， 而且没有报错、没有任何提示 —— 等发现的时候原文件已经被替换掉了。 新版显式 -map 0:v:0 -map 0:a? 并带 -map_metadata 0 -map_chapters 0。

8哪些地方没有提升（以及代价）

把不好的一面也摆出来，否则这份报告没有价值。

  • 单文件 H.265 / AV1 编码没有变快，实测 +7% / +13%，落在噪声区间。这两个编码本来就自动并行，本轮改的是上限而非速度。
  • 满并发时吞吐略降 5%（8×H.265：14.75s → 15.45s）。这是限流的代价，换 CPU 占用 −9.4%。习惯「开满走人」的用户感知不到好处。
  • AV1 输出体积 +1.5%，来自 tune=0（PSNR 取向）。画质取向变了，不是退化，但如果你的目标是极限体积，需要知道这一项。
  • VP9 的 CPU 总时间反而涨了 12%（41.0s → 46.1s）。多核并行必然有同步开销，只是墙钟砍半更划算。笔记本电池供电时要注意。
  • 测试素材是合成的，绝对耗时（比如 H.265 单文件 2 秒）远低于真实影片。所有结论只取新旧相对差，不要用绝对值推算你的素材。

9怎么复现这些数字

# 1. 取出已发布的 1.1.0 作为基线（不动当前工作区）
git worktree add /tmp/vc-base HEAD

# 2. 造素材：1080p30 / 5s / 双音轨
ffmpeg -y -f lavfi -i "testsrc2=size=1920x1080:rate=30:duration=5" \
       -f lavfi -i "sine=frequency=440:sample_rate=48000:duration=5" \
       -f lavfi -i "sine=frequency=220:sample_rate=48000:duration=5" \
       -vf "noise=alls=10:allf=t+u" -c:v libx264 -preset medium -crf 14 \
       -pix_fmt yuv420p -c:a aac -b:a 128k -map 0:v -map 1:a -map 2:a src5.mp4

# 3. 让两套代码各自生成参数，再交给同一个 ffmpeg 实跑
#    （脚本见 tests/bench/bench-encode.js，耗时口径取自 -benchmark）
node tests/bench/bench-encode.js

# 4. 界面开销：用 jsdom 起插件，统计 state.tasks 的按下标访问次数
node tests/bench/bench-ui.js   old 100
node tests/bench/bench-ui.js   new 100

# 5. 真实探测吞吐：把 core 桩的 probe 换成真 ffprobe
node tests/bench/bench-probe.js old 25
node tests/bench/bench-probe.js new 25

# 6. 提交阶段：copyFile vs rename
node tests/bench/bench-commit.js

# 7. 回归闸门（必须全绿）
./tools/verify.sh
